# 매매 실행 주기와 진입 품질 게이트

**작성일**: 2026-08-16
**상태**: 구현 완료

---

## 1. 문제

분석은 심볼당 1시간에 한 번 돌고, `execute` cron은 `7 13-21 * * 1-5` — 정규장 게이트를 통과하는
것은 하루 **6틱**, 그중 진입 창(ET 11:00–15:00) 안은 **4틱**이다. 즉 가격 조건을 판정하는 최소
간격이 **60분**이었다.

운영자가 보고한 시나리오:

> 분석이 $150에 진입하라고 했는데, 10분 뒤 $150을 찍고 30분 뒤 $180이 되면 매수 기회를 놓친 것 아닌가.

놓친 것으로 끝나지 않는다. 실제로는 **더 나쁘게** 동작했다.

1. 11:07 틱 — $152, 점수 68 → hold
2. 11:20 — $150 터치. **다음 틱까지 아무도 보지 않는다**
3. 12:07 틱 — $180. 기술 분석 신선도 한도(1Hour 기준 2시간) 안이라 **같은 분석**이 그대로
   쓰이고 점수는 여전히 매수 → **시장가로 $180 매수**

손절선·목표가는 $150 기준 분석에서 나오는데 진입만 $180이므로 리스크:리워드가 뒤집힌다.
매수 판정에 가격 조건이 하나도 없었기 때문이다 — `actionRecommendation.entryPrices`(권장 진입
구간)는 `lib/analysis/trade-gate.ts`의 프롬프트 텍스트로만 들어가고 규칙에서는 읽히지 않았다.

같은 결함이 청산에도 대칭으로 있었다. `evaluateExistingPosition`도 60분에 한 번만 돈다 — 손절
라인이 뚫려도 최대 60분 방치된다. 진입 기회 손실은 기회비용이지만 이쪽은 **실현 손실**이다.

**근본 원인은 하나다: 가격 조건 판정이 전부 execute 틱 안에만 있고, 그 틱이 분석 주기(=LLM
비용)에 묶여 있었다.** 가격 감시는 FMP quote 한 번이라 사실상 공짜인데도 같은 시계를 썼다.

## 2. 결정

### 2.1 실행 주기를 분석 주기에서 분리하고, 설정으로 뺀다

`execute` cron 스케줄을 `7-59/5 13-21 * * 1-5`로 바꾸고(5분마다 호출), 실제 실행 여부는
`lib/strategy/execute-interval.ts`의 게이트가 `config.execute_interval_min`으로 정한다.
허용값은 **5·10·15·20·30·60**, 기본 **10분**.

**왜 스케줄 문자열을 직접 설정으로 만들지 않았나** — node-cron 태스크는 등록 시점에 고정되므로
스케줄을 바꾸려면 재등록, 즉 프로세스 재시작이 필요하다. 게이트는 대시보드에서 바꾼 즉시 다음
틱부터 먹고, 건너뛴 틱의 비용은 설정 조회 한 번이다.

**왜 :07 오프셋을 유지하나** — 분석 cron이 정각에 시작한다. 정각에 점수를 매기면 이번 사이클
분석이 저장되기 전이라 한 사이클 묵은 값을 읽는다. 게이트는 `(분 − 7) mod 간격 === 0`이므로
간격 60분이면 실행 시각이 종전 스케줄과 **분 단위로 동일**하다. 허용값을 60의 약수로만 둔 이유도
같다 — 그래야 시(hour) 경계에서 주기가 끊기지 않는다.

**게이트를 감사 행보다 앞에 둔 이유** — 건너뛴 틱까지 `cron_runs`에 남기면 60분 설정에서 하루
78행 중 6행만 실제 실행이 되어 감사 로그가 잡음으로 덮인다. 설정 조회가 실패하면 기본값으로
**진행**한다: DB 일시 장애로 매매 틱이 통째로 사라지는 쪽이 더 나쁘고, 실행에 들어가면 기존 감사
경로가 오류를 제대로 남긴다. `?force=1`은 수동 트리거용 우회다.

**기본값이 5분이 아닌 이유** — 한 틱은 심볼당 FMP 호출 2회(현재가 quote + 컨플루언스 봉)를 쓴다.
10분은 반응 지연을 1/6로 줄이면서 호출량을 12배가 아닌 6배로 묶는 지점이다.

### 2.2 진입 구간 상단 게이트 (`entry_out_of_zone`)

현재가가 `entryPrices`의 최대값 + 1%를 넘으면 매수/추가매수를 건너뛴다
(`lib/strategy/entry-zone.ts`).

- **상단만 본다.** 구간 아래(=더 싼 가격)는 매수에 불리한 방향이 아니고, 근거가 무너진 하락이라면
  다음 분석에서 점수가 먼저 떨어진다. 하한을 두면 "분석이 원한 것보다 싸다"는 이유로 매수를
  거르게 되는데 그건 이 게이트가 막으려는 문제가 아니다.
- **판단 재료가 없으면 통과**(fail-open). `entryPrices`가 없거나 전부 비정상이면 게이트가 없던
  때와 같이 동작한다. 진입 품질을 높이는 장치이지 매수의 전제조건이 아니다.
- **사이징 게이트보다 앞**에 둔다. 어차피 사지 않을 주문에 25초짜리 LLM 호출을 태우지 않는다.
- **매도에는 걸지 않는다.** 원칙 7과 같은 이유 — 진입만 막는다.
- 허용 오차 1%: 구간은 AI가 낸 근사치이고 현재가는 틱 단위로 움직인다. 상단에 정확히 붙은 값을
  소수점 차이로 걷어내면 게이트가 아니라 잡음이 된다.

### 2.3 재진입 쿨다운 (`entry_cooldown`)

같은 심볼을 다시 매수하기까지의 최소 간격. `config.entry_cooldown_min`, 기본 **60분** =
실행 간격이 60분이던 시절의 동작. 0이면 꺼진다.

**2.1의 필수 동반이다.** 실행 간격을 10분으로 줄이면 매수 신호가 살아 있는 한 틱마다 분할 진입이
나가므로, 쿨다운이 없으면 한 종목이 `max_trades_per_day`를 하루치 통째로 먹는다. 진입 간격을
실행 간격에서 분리하는 것이 목적이다.

전용 쿼리 대신 기존 `getRecentTrades(db, 100)`를 한 번 읽어 메모리에서 접는다 — 쿨다운이 보는
범위는 길어야 몇 시간이고, 기본 한도 20건이면 100행은 며칠치다. `mode: 'skipped'` 행(잔고 부족
기록, 수량 0)은 체결이 아니므로 세지 않는다.

### 2.4 청산 쪽: 게이트가 아니라 트리거를 더한다

운영자 질문은 "매도가에도 게이트가 필요한가"였다. **막는 게이트는 넣지 않는다** — 가격 조건으로
청산을 막는 것은 손실을 키우는 방향이고, 진입 fail-closed / 청산 fail-open이라는 이 시스템의
기존 비대칭(원칙 7, AI 사이징 게이트 설계 §8)과 정면으로 어긋난다.

대신 진짜로 빠져 있던 것을 채운다: **분석이 명시한 손절가·익절가를 실제 트리거로 쓴다.**

`actionRecommendation.stopLoss` / `takeProfitPrices`는 core가 유효성 보정(`reconciledLevels`)까지
해 주는 값인데도 사이징 게이트 프롬프트에만 들어가고 규칙 엔진은 읽지 않았다. 그 결과
`fixed_exit_enabled`가 기본 꺼짐인 상태에서 활성 손절 경로는 지지선 이탈·추세 반전·하락
컨플루언스뿐이었다 — 전부 **간접** 신호다. "여기서 자른다"고 분석이 명시한 가격은 아무도 보지
않았다.

`evaluateExistingPosition` 우선순위에 두 줄이 들어간다:

| 순위 | 트리거 |
|---|---|
| 1 | 고정 손절 % (`fixedExitEnabled`) — `hard` |
| **1.5** | **분석 손절가 이탈 (`aiStopLoss`)** |
| 2 | 지지선 이탈 |
| 3 | 기술적 추세 반전 |
| 3.5 | 하락 지표 컨플루언스 |
| 4 | 고정 익절 % (`fixedExitEnabled`) |
| **4.5** | **분석 익절가 도달 (`aiTakeProfit`)** |
| 5 | 저항선(98%) / 목표가(95%) 근접 |
| 6 | 뉴스 악재 + 비강세 |

배치 근거: **운영자가 그은 선 → 분석이 그은 선 → 간접 신호** 순서다. 둘 다 `hard`를 세우지
않는다 — 분석에서 파생된 판단이지 절대 리스크 한계가 아니므로 사이징 게이트가 얼마나 자를지
정한다. 보정값(`reconciledLevels`)이 있으면 그쪽이 이긴다: core가 "못 쓴다"고 판정한 숫자로
청산하면 안 된다.

명시 가격이므로 5번과 달리 근사(95%/98%)를 쓰지 않는다.

## 3. 되돌리는 법

| 바꾼 것 | 끄는 법 |
|---|---|
| 실행 주기 | 설정 > 매매 실행 주기 = 60분 → 종전 스케줄과 실행 시각 동일 |
| 재진입 쿨다운 | 설정 > 투자 관리 > 재진입 최소 간격 = 0 |
| 진입 구간 게이트 | 전용 스위치 없음 — 분석에 `entryPrices`가 없으면 자동으로 통과 |
| 분석 손절/익절가 | 전용 스위치 없음 — 지지선 이탈과 같은 "항상 활성" 계층이다 |

뒤의 둘에 스위치를 두지 않은 이유는 같다: 둘 다 분석이 이미 내놓은 값을 읽는 것뿐이고, 지지선
이탈·저항선 근접 같은 기존 분석 파생 트리거에도 개별 스위치가 없다. 계층 자체를 끄는 스위치는
`fixed_exit_enabled`가 아니라 워치리스트에서 종목을 빼는 것이다.

## 4. 알려진 한계

- **여전히 폴링이다.** 10분 간격은 $150 터치를 최악 10분 뒤에 본다. 정확히 $150에 잡으려면
  브로커에 지정가 주문을 걸어야 한다(Toss API는 `LIMIT` + `price`를 지원하지만
  `IssueOrderRequest`가 `'MARKET'`으로 좁혀져 있고, reconcile의 30분 타임아웃 취소 규약도 함께
  손봐야 한다). 이번 범위 밖이다.
- **분할 진입과 진입 창의 상호작용은 그대로다.** 기본 창(ET 11:00–15:00)에서 실행 간격 10분이면
  진입 가능 틱은 24개지만 쿨다운 60분이 심볼당 4회로 묶는다 — 종전과 같은 숫자다.
- **`entry_out_of_zone`은 분석 품질에 종속된다.** `entryPrices`가 지나치게 좁으면 매수가 거의
  나가지 않는다. 그 경우 감사 로그의 `detail.entryZone`이 원인을 그대로 보여준다.
