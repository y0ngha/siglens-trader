# 진입 시간 창 (Entry Window) 설계

작성일: 2026-08-15 · 관련 코드: `lib/strategy/entry-window.ts`, `api/cron/execute.ts`, `api/config.ts`

## 1. 요구

운영자 요청: "개장 직후 변동성과 마감 임밸런스를 피해 조용한 시간대에만 진입하고 싶다."

## 2. 왜 cron 창을 좁히지 않았나

`execute` cron(UTC `7 13-21 * * 1-5`)의 스케줄을 좁히는 것이 가장 짧은 diff다. 그리고 틀렸다.

이 cron은 두 가지를 한다: (1) 보유 포지션 재평가 → 손절/익절/청산, (2) 워치리스트 신호 스코어링
→ 신규 진입. 스케줄을 좁히면 **둘 다** 죽는다. 마감 1~2시간 동안 손절 경로가 사라지고 오버나이트
갭이 무방비가 된다 — 정확히 리스크가 가장 큰 구간에서.

저장소 원칙 7: *리스크를 줄이는 유일한 경로를 막는 회로차단기는 그 자체가 결함이다.* 일일 손실
한도가 조기 `return` 대신 `entryBlock`을 세우는 이유와 같다. 그래서 창은 스케줄이 아니라 **진입
게이트**로 구현했고, cron 스케줄 표는 한 줄도 바뀌지 않았다.

## 3. 왜 ET 고정인가

창을 UTC나 KST에 고정하면 서머타임마다 장중에서 한 시간씩 밀린다. 회피하려는 현상 — 개장 갭,
첫 30분 변동성, 마감 MOC 임밸런스 — 은 전부 **ET 기준**으로 일어나므로, UTC 고정 창은 반년마다
목적 자체가 깨진다. 여름에 "개장 90분 후"였던 창이 겨울엔 "개장 30분 후"가 된다.

`Intl.DateTimeFormat('en-US', { timeZone: 'America/New_York', ... })`로 환산한다. `lib/strategy/`는
외부 패키지 import 금지지만 `Intl`은 JS 표준 빌트인이고 결정론적이며 I/O가 아니다 — 순수성 규칙에
걸리지 않는다. 포매터는 생성 비용이 커서 모듈 로드 시 한 번만 만든다.

## 4. 기본값 근거

**ET 11:00–15:00.** 개장(09:30 ET) 후 첫 90분과 마감(16:00 ET) 전 마지막 60분을 피한다. 앞쪽은
갭 정리와 개장 경매 잔열이, 뒤쪽은 MOC 임밸런스가 지배하는 구간이라 신호 대비 슬리피지가 가장
나쁘다. 한국 운영자 기준 여름 KST 00:00–04:00, 겨울 01:00–05:00.

끝은 **배타적**이다(`start <= m < end`). 정규장 마감을 16:00 exclusive로 보는 core
`getEtSessionStatus` 관례와 맞춘다.

자정을 넘는 창은 지원하지 않는다(`start < end` 강제). 미국 정규장은 자정을 넘지 않으므로 그런
값은 설정 실수이지 의도가 아니고, 랩어라운드를 허용하면 `start === end`가 "0분"인지 "하루 전체"인지
영원히 모호해진다.

## 5. 리스크 차단기와의 우선순위

창 검사는 `entryBlock`을 세우는 코드 중 **가장 먼저** 실행된다. 아래 차단기들(일일 거래 한도,
일일 손실 한도)은 평범한 대입이라 둘 다 해당하면 나중 것이 이긴다. 창 밖인 것보다 손실 한도에
걸린 것이 운영자에게 훨씬 중요한 사실이므로, 그쪽이 `cron_runs.outcome`에 남아야 한다.

창은 **리스크 사건이 아니다.** 따라서:

- `forceFullExit`를 켜지 않는다 → 청산 사이징 게이트가 그대로 동작한다(부분 청산 가능).
- 이메일을 보내지 않는다 → 정상 상태이고 시간당 여러 번 발생한다.
- 신호 매도는 그대로 통과한다 → `if (entryBlock && signalScore.signal !== 'sell')` 가드가
  기존 차단기와 동일하게 적용된다.

| 상황 | 동작 |
|---|---|
| 창 밖 + 보유 포지션 없음 | 조기 반환. `{ skipped: true, reason: 'outside_entry_window', entryWindow, timezone }`, `cron_runs.status='skipped'`, `outcome='outside_entry_window'` |
| 창 밖 + 보유 포지션 있음 | 실행 계속. 재평가·손절·청산 정상 동작. 응답에 `exitOnly: true` + `entriesBlockedBy: 'outside_entry_window'` |
| 창 밖 + 매수 신호 | `entry_blocked` 결정 기록. `detail.entryWindow`에 당시 창을 남겨 "왜 그날 안 샀나"를 사후에 답할 수 있게 한다 |
| 창 밖 + 매도 신호 | 통과 |
| 시각 판독 실패 (`Invalid Date`) | **차단**. AI 사이징 게이트의 진입 fail-closed / 청산 fail-open 비대칭을 그대로 따른다 — 시계를 모르는 상태에서 새 리스크를 여는 것보다 한 틱 쉬는 쪽이 싸다. 청산은 이 함수를 거치지 않는다 |

## 6. 설정과 끄는 법

`config.entry_window` = `{ start: 'HH:MM', end: 'HH:MM' }` (ET). `POST /api/config`의
allowlist에 추가됐고, 형식·범위·`start < end`·미지 키를 전부 검증해 **거부**한다.

**끄려면 `{ start: '00:00', end: '24:00' }`을 저장한다.** `'24:00'`은 1440(하루 끝)으로 파싱되고
`m < 1440`은 항상 참이라 모든 시각이 창 안이 된다. 별도 플래그를 두지 않은 이유는
`score_weights.confluence = 0`이 컨플루언스 축의 off-switch인 것과 같다 — 값 자체로 표현 가능한
상태에 불리언을 하나 더 얹으면 두 소스가 어긋날 수 있다.

런타임 파싱(`parseEntryWindow`)은 잘못된 값을 조용히 기본 창으로 되돌린다. API 검증은 그걸 쓰지
않고 별도로 거부한다: 런타임 fallback은 손상된 DB 행에 대한 방어이고, API에서 같은 fallback을
쓰면 운영자의 오타가 조용히 삼켜진다. 다만 `'HH:MM' → 분` 변환(`parseTimeOfDay`)은 공유해서,
대시보드가 받아준 값을 런타임이 다르게 읽는 일이 없게 했다.

## 7. 대시보드 UI

설정 화면(`src/pages/Settings.tsx`)의 **진입 시간 창** 섹션에서 조정한다. API 직접 호출은 더
이상 필요 없다 — 운영자가 요청한 기능을 화면에서 못 바꾸면 그건 미완성이다.

- **시간 입력은 `<input type="time">` 두 개.** `HH:MM` 형식 강제와 위젯을 브라우저가 공짜로
  준다. 커스텀 시간 피커도 문자열 파싱도 두지 않았다.
- **끄기는 별도 ON/OFF 토글.** `'24:00'`은 `type="time"`이 표현할 수 없는 값이라 off-switch를
  시간 입력으로 표현할 방법이 없다. OFF면 저장 시 `{ start: '00:00', end: '24:00' }`을 보내고
  시간 입력은 disabled가 된다. 반대로 저장된 값이 off-switch면 토글은 OFF로 보이되 입력에는
  **기본 창(11:00/15:00)** 을 채운다 — 다시 켰을 때 빈 칸이 보이면 안 되기 때문.
- **ET 기준임을 화면에 못박는다.** 라벨이 `진입 시작 (ET)` / `진입 종료 (ET)`이고, 그 아래
  현재 값의 한국시간 환산을 여름·겨울 둘 다 적는다:
  `ET 11:00–15:00 = 한국시간 여름 00:00–04:00 / 겨울 01:00–05:00`.
  환산은 **순수 산술**이다 — KST = ET + 13h(EDT) 또는 + 14h(EST), 상수 두 개가 전부.
  기준 날짜가 없는 상태에서 `Intl`/`Date`로 오프셋을 뽑으려 하면 오히려 틀린 답이 나온다.
- **"청산은 제한되지 않는다"를 상시 노출한다.** "밤에 손절이 안 되나?"는 위험한 오해라
  섹션에 한 줄로 고정해뒀다: *청산·손절은 정규장 내내 그대로 실행됩니다 — 이 창은 신규 진입만
  제한합니다.*
- **`start >= end`는 클라이언트에서 먼저 막는다.** 저장 버튼이 disabled가 되고 인라인 에러가
  뜬다. 서버 400은 그대로 남아 있지만(§6), 이미 아는 오류로 왕복할 이유가 없다.

`DEFAULT_ENTRY_WINDOW` / off-switch 문자열은 `src/` 안에 다시 적혀 있다. `src/`가 `lib/`를
import하지 않는다는 레이어 규칙 때문이며, `analysis_timeframe`이 같은 방식으로 미러링돼 있다.

## 8. 알려진 절충

- **진입 기회가 준다.** 기본 창은 정규장 6.5시간 중 4시간이다. 조용한 구간을 노린다는 것은 그
  구간 밖에서 뜨는 신호를 전부 포기한다는 뜻이고, 갭 상승 추종처럼 개장 직후에만 존재하는
  엣지는 구조적으로 잡을 수 없게 된다. 이건 버그가 아니라 요청받은 절충이다.
- **분석 cron은 그대로 돈다.** 창 밖에도 technical/news/options는 정상 실행되어 LLM 비용을 쓴다.
  창 밖 분석은 그 자체로 무가치하지 않다(창이 열릴 때 읽을 최신 스냅샷이 된다)므로 손대지 않았다.
- **창이 좁으면 `cron_runs`에 `skipped` 행이 늘어난다.** 무포지션 상태에서 창 밖이면 조기
  반환하므로, 하루에 여러 번 `outside_entry_window` skip이 기록된다. 할 일이 없는 틱이므로
  정상이지만, cron 헬스 대시보드에서 "왜 이렇게 많이 건너뛰나"로 읽힐 수 있다.
- **휴장일·반일장은 고려하지 않는다.** 창은 시각만 본다. 상위 게이트인 `isEtRegularSessionOpen`이
  요일과 시각을 보고, 공휴일 판정은 `execute.ts`의 별도 게이트가 담당한다. 반일장(13:00 ET 마감)
  에는 창의 뒤쪽 2시간이 장 마감 이후에 걸리는데, 이 경우 상위 게이트가 이미 `market_closed`로
  끊으므로 무해하다.
